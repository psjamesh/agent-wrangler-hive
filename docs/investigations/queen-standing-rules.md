# Where queen standing rules should live

Investigation, 15 November 2026. This is a proposal, not a change to Hive policy or agent permissions.

## Recommendation

Do not introduce `HIVE.md`. Give each repository a small `AGENTS.md` for engineering facts, with a `CLAUDE.md` entrypoint that imports it. Put Hive operating behaviour in the existing role skills, tools and watchdog; put configurable choices in the existing settings. Implement delivery authority through the accepted [delivery policy design](../design/delivery-policy.md). Keep task-specific direction in the hive's saved queen instructions and work record.

The problem is not the filename of the private rules. It is that an individual queen has been compensating for product gaps, retaining fixed-bug workarounds, and interpreting personal choices as universal defaults. Moving all that prose into a public file would make it reviewable, but would still require every queen to simulate missing product behaviour. It would also preserve several contradictions.

Use one authoritative home for each fact. A brief or instruction file can point to it; it should not copy a second policy. A fresh queen must be able to explain its behaviour from installed Hive defaults, visible configuration, repository instructions and the current bead, without private memory.

Source findings below describe those snapshots, not proof that every running agent has refreshed its code or tool schema. Local configuration and installation provenance were read only where needed; their private values and locations are omitted.

This was a source and configuration investigation. No browser was launched, no runtime code changed, and no full test suite was run. Existing tests were inspected as evidence of intended contracts; their presence is not a claim that they passed in this investigation. Personal authority cannot be proved by code: the operator's instruction establishes it, while code shows whether a mechanism exists to represent it.

## AGENTS.md, HIVE.md, settings or skills?

### Who actually receives the instructions

At the inspected snapshots, **Hive has neither `AGENTS.md` nor `CLAUDE.md`**. Core has a short **`AGENTS.md` containing public-content constraints**, and its **`CLAUDE.md` contains `@AGENTS.md`**. Core's detailed safe test instructions are in `CONTRIBUTING.md`, not its agent entrypoint. [Core agent instructions][core-agents], [Claude entrypoint][core-claude], [contribution guide][core-contributing].

Core's [skill plumbing][core-skills] gives Claude plugin directories and an appended mandatory nudge; Codex receives a skill catalog and mandatory nudges through developer instructions. Hive's [manifest](../../server/manifest.js) chooses the queen and worker skills by membership/role, including reviewers through the worker role. That delivery is independent of repository cwd. Catalog availability does not mean the full skill was read; the short `WRANGLER.md` nudge exists to prompt that read.

Repository instructions have a narrower reach. Codex uses its native `AGENTS.md` convention; Claude needs its native `CLAUDE.md` entrypoint/import. The Wrangler adapters do not make arbitrary `AGENTS.md` or `HIVE.md` content universal. A queen coordinating several repos from a separate working directory will not automatically receive each repo's root instructions. Reviewers and workers must be launched into the assigned checkout and read its instructions; explicitly identify them in the brief when cwd or provider discovery is uncertain. Neither convention guarantees compliance, and a running session should not be assumed to reload changed guidance.

Saved `queen_instructions` are included in the queen launch brief and full-cell `hive_context`. **Bead-scoped context currently omits them, reviewer policy and Codex approvals.** Workers/reviewers therefore cannot be assumed to receive everything the queen saw. This is a reason to project relevant effective configuration, not to expose all queen-only notes or copy them into worker briefs. [Launch instructions](../../server/sessions.js), [full and bead context](../../server/tools.js).

## How a queen should handle the next lesson

1. **Capture the observation on the affected bead.** Record expected versus observed behaviour, source/version and a safe reproduction or evidence. Do not promote one incident directly into a permanent instruction. Keep sensitive operational details in the private work record.
2. **Check current reality before prescribing a workaround.** Look for a shipped fix, installed-versus-loaded mismatch, stale client schema, conflicting task instruction or existing setting. State what is known and what remains unverified. An authentication failure, approval refusal and product restriction need different remedies.
3. **Choose the owner and one durable home.** A deterministic invariant belongs in a tool/test; detectable neglect belongs in watchdog attention; necessary judgment belongs in a role skill. An engineering fact belongs in repo instructions/docs. A genuine preference belongs in existing settings or human-authored queen instructions. Installation paths and provider grants belong in operator configuration. An expired workaround needs no replacement rule.
4. **Create a bounded follow-up when the default is deficient.** Describe the default that would have prevented the incident and its acceptance, under the right workstream. Link real prerequisites and arm only work that is sufficiently scoped. Do not silently change global policy or infer a new user preference from frustration. Route a genuine unresolved decision through one in-topic Hive request.
5. **Make any interim exception visible and temporary.** Put its limited scope, reason and removal condition on the bead; relay only the necessary instruction to the affected worker. Keep the exception recognizable as an exception, so it does not make a faulty product default appear successful.
6. **Verify adoption with fresh agents and retire the exception.** Check tool behaviour and what a newly launched queen/worker/reviewer actually receives, on both providers, without private memory. Record delivery evidence. Remove a temporary rule only after its replacement or obsolescence is verified and the operator authorizes memory retirement. This investigation does not edit those memories.

Put this short routing procedure in the queen skill. It should not require a new lesson registry, a second policy document, or a setting for each lesson. Existing beads already hold the evidence and implementation work.
